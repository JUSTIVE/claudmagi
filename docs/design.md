# claudmagi — 디자인 노트

참고 영상: `~/Downloads/HRxKPCOaoAAn4b7.mp4` (854×480, 15fps, 15.4s). 프레임 추출 관찰 결과.

## 전체 인상
- 참고 영상의 배경은 선명한 주황(약 `#F04A0E`)이지만, claudmagi는 배경을 흰색으로 쓰고 선 위를 흐르는 작은 패킷을 그 주황으로 칠한다(#16).
- PCB 트레이스 / 지하철 노선도 느낌의 얇은 검은 선들이 수평 → 45° 대각선 → 수평으로 흐른다.
  대각선 구간은 서로 평행하게 묶여 "밴드"를 이룬다.
- 선 위에 검은 둥근 사각형 "칩"이 얹혀 있고 라벨은 민트 그린(약 `#3BE38A`) 대문자 고정폭 글꼴.
  대각선 위의 칩은 45° 회전, 수평 구간의 칩은 수평.
- 선을 따라 작은 점(패킷)이 이동한다 — claudmagi에서는 주황색.

## 상태 표현
| 상태 | 표현 |
|------|------|
| 작업 중 (연결) | 검은 칩 + 녹색 라벨, 선이 칩을 관통. 다크 테마에서는 흰 칩 + 짙은 녹색 라벨(#32) |
| 서브에이전트 | 부모 세션 칩 오른쪽, 같은 선 위에 더 작은 칩(높이 16)으로 사슬처럼 이어짐(#12, #13). 실행 중이면 연결, 끝나면 분리됐다가 45초 뒤 사라짐 |
| 입력 필요 / 완료 (세션, 분리) | 선이 느슨한 케이블 모양(S자 파형)으로 늘어진 뒤 홈(notch)이 파인 검은 소켓 블록에서 끝남. 칩은 소켓에서 떨어져 나가 있다. 흰색·다크 테마에서 **입력 필요는 주황 칩 + 검은 라벨**, **완료(idle)는 어두운 적갈색 칩 + 앰버 라벨**(#50) — 기다리는 쪽이 더 눈에 띈다. 오렌지 테마는 주황 칩이 배경에 묻히므로 입력 필요 적갈 + 앰버, idle은 한 단계 더 어두운 적갈 + 흐린 앰버 |
| 완료 (서브에이전트, 제자리) | 서브에이전트는 분리되지 않는다: 선이 그대로 관통한 채 바탕만 idle 색으로 가라앉고 높이가 16 → 12로 줄어든다. 45초 뒤 페이드아웃 (#53) |
| Linear 노드 (왼쪽 끝) | 세션의 Linear 이슈. 보드 **왼쪽 끝에 붙어** 있고 레인은 이 노드의 오른쪽 모서리에서 시작한다 — 작업이 티켓에서 나온다는 뜻. 상태(`state.type`)를 색으로: backlog·미조회 흐린 테두리 · todo 잉크 테두리 · **진행 중 앰버 채움** · **완료 검정 채움** · 취소 흐린 테두리. 클릭하면 **Linear 데스크톱 앱**으로 (#57, #58, #60) |
| PR 커넥터 (오른쪽 끝) | 세션에 연결된 GitHub PR들. **하나의 티켓에 PR이 여러 개일 수 있어** 오른쪽 끝 기준으로 최신이 바깥쪽이 되게 가로로 이어 붙이고, 체인이 210px를 넘으면 오래된 것부터 `+n` 배지로 접는다. 트레이스는 체인의 가장 왼쪽 노드에서 끊긴다 (#63). 보드 **오른쪽 끝에 붙어** 한 열로 정렬되고, 트레이스가 왼쪽 모서리로 들어가 거기서 끊긴다 — 작업이 보드 밖으로 나간다는 뜻. 핀 없이 **몸통 색이 상태 전부**를 나타낸다: draft 잉크 테두리 · **open 녹색 테두리** · **approved 녹색 채움** · **체크 실패 오렌지 채움** · **merged 검정 채움** · closed 흐린 테두리. 테두리는 진행 중, 채움은 결판난 것. **CI가 돌고 있으면 테두리를 노란색(1.7px)으로** 덮어쓴다 — 상태가 아니라 겹쳐 그리는 층이라 채워진 커넥터 위에도 보인다(재실행 중인 approved 등). 클릭하면 PR이 열린다 (#56, #57, #58, #62) |
| 끝난 레인 | Linear가 완료 + PR이 **하나 이상 머지되고 나머지도 전부 머지/클로즈**(진행 중인 게 없음) + 세션이 idle이면 그 레인의 트레이스를 굵게(1.6 → 2.9) 그린다. 셋 다 맞아야 하므로 "더 할 일이 없는 줄"을 한눈에 고를 수 있다 (#61) |
| 호버 | 칩 주위 검은색 1.5px 외곽선(#11), 포인터 커서 |

색은 라이트 테마 기준으로 정하고, 나머지 테마는 팔레트 항목으로 옮겨 따라가게 한다 — "검정 채움"은 `pal.chip`이라 다크 테마에서 흰 채움이 되고, 오렌지 테마의 실패색은 주황이 배경에 묻히므로 `#8C1D18`이다. (#58)
| 등장 | 아래→위 순으로 칩이 주황빛 반투명에서 검정으로 페이드인 |
| 스크롤 | 세로 스크롤로 더 많은 레인을 볼 수 있음 |

## claudmagi 매핑
- 세션 1개 = 칩 1개. 라벨은 `~/.claude/sessions/<pid>.json`의 `name` 대문자.
- `status == busy` 이고 `waitingFor` 없음 → 연결 상태.
- `waitingFor` 있음(권한/다이얼로그) 또는 `tempo/state == blocked` → 분리 + 앰버(입력 필요).
- `status == idle` → 세션은 분리 + idle 색(적갈 칩 + 앰버 라벨), 서브에이전트는 제자리에서 가라앉음(#53).
- PR → 세션 트랜스크립트(`~/.claude/projects/<slug>/<sessionId>.jsonl`, 슬러그가 다르면 projects 전체를 훑어 찾는다 — `subagents` 디렉터리에서 유도하면 서브에이전트를 안 띄운 세션이 통째로 빠진다 #65) 뒤쪽 2MB에서 `message.content` 블록 안의 `github.com/<owner>/<repo>/pull/<n>` **전부**(번호 오름차순, 세션당 최대 4개). `cwd`의 origin remote와 repo가 일치해야 한다. 상태는 `gh pr view --json`, 60초 TTL 캐시. 조회는 **워커 스레드 3개**가 맡고 `snapshot()`은 캐시만 읽는다 — 한 건에 1초 넘게 걸려서 세션 폴링(1초) 안에 두면 보드가 다 뜨는 데 20초 넘게 걸렸다(#64). 체크 집계는 `CheckRun`이면 `status`(완료 전) → `conclusion`(완료 후), `StatusContext`면 `state`를 본다. `QUEUED`/`IN_PROGRESS`/`PENDING`/`WAITING`/`REQUESTED`는 진행 중, `CANCELLED`·`SKIPPED`는 성공도 실패도 아니다. `--prs`로 터미널에서 확인. (#56)
- Linear 이슈 → 세션 이름이 `ABC-123` 꼴이고 (a) 트랜스크립트의 `linear.app` 링크나 PR 제목이 같은 키를 반복하거나 (b) 팀 접두사가 보드가 실제 링크에서 본 팀이면 그 이름을 쓴다. 아니면 PR 제목의 `[ABC-123]` 태그. **링크만 된 키는 단독으로는 채택하지 않는다** — 티켓을 읽은 것과 작업한 것은 다르다 (#65). 이 규칙이 `YOSHI-60`을 티켓으로 오인하지 않으면서 `PJM-1924`는 통과시킨다. 워크스페이스 슬러그는 링크에서 가장 많이 본 것. 상태는 없다 — `orca linear issue`가 이 머신에서 `runtime_unavailable`이다 (#43의 warpctrl과 같은 상황). (#57)
- Linear 상태 → `orca linear issue <KEY> --json`의 `result.issue.state.type` (`triage`/`backlog`/`unstarted`/`started`/`completed`/`canceled`/`duplicate`). **Orca 앱이 떠 있어야** 하고, 닫혀 있으면 `runtime_unavailable`이라 노드는 키만 보여준다. URL도 `result.issue.url`을 그대로 쓴다(슬러그 조립보다 정확). 60초 TTL, 실패는 5분 TTL(닫힌 Orca를 매초 두드리지 않기 위해). 조회는 워커 스레드 1개 — `orca`는 로컬 앱 하나와 이야기하므로 병렬로 물어봐야 얻는 게 없다 (#64). (#58)
- 클릭 → 해당 세션의 Warp 탭으로 이동. PR 노드는 브라우저로, Linear 노드는 `linear://<workspace>/issue/<KEY>` 딥링크로 데스크톱 앱에서 연다. 스킴이 안 먹으면 웹 URL로 폴백한다. Linear.app은 이 스킴을 Info.plist가 아니라 런타임에 등록하므로 LaunchServices에만 보인다 (#57, #60) (`WARP_FOCUS_URL=warp://session/<uuid>` 를 프로세스 환경에서 읽어 `open`).

## 치수(디자인 단위)
- 기준 크기 980×620. 창이 커져도 자동 확대는 하지 않고(#19) 레인과 스트라이프를 더 채운다. 크기는 사용자 배율(⌘+/⌘-/⌘0, ⌘+휠, 상태바 −/+)로만 0.5~3배 조절한다(#18).
- 레인은 두 줄씩 짝: 짝 안 간격 22, 짝 사이 추가 간격 24(#14, #29, #31, #35, #39). 선 굵기 1.6, 대각선 낙차 128, 모서리 반경 8
- 레인은 하나의 계단: 레인 i는 폭의 62% 지점에서 시작해 자신이 내려간 만큼 왼쪽에서 꺾인다 → 꺾임이 45° 스트라이프를 이룬다.
  넓은 창에서는 폭의 55% 간격으로 스트라이프를 반복(`bands`)해 오른쪽 아래까지 채운다. 이 구성은 선이 절대 교차하지 않는다.
- 첫 스트라이프의 빗변(수직 낙차)은 레인 i마다 `128 + 12·i`(#45, `first_diag`; 최소 24, 다음 스트라이프 시작 전에 끝나도록 폭에 따라 상한). 평행한 45° 빗변은 길이가 달라도 교차하지 않고, 지나고 나면 레인 간격이 레인당 12씩 넓어져 선이 부채꼴로 퍼진다. 두 번째 스트라이프부터는 이 넓어진 오프셋(`fanned_offset`)을 기준으로 다시 128 낙차의 계단.
- 레인 수는 `LEAD_LANES(8) + 세션 수 + TRAIL_LANES(6)`로 고정(#45). 창이 커져도 레인은 늘지 않고 스트라이프만 는다. 위쪽 보조 레인 8개(`LEAD_LANES`)는 오른쪽 상단을 채우며, 음수 인덱스라 첫 빗변이 짧다.
- 세션 슬롯 k → 레인 `LEAD_LANES + k`(짝의 두 줄 모두 사용, #31). 세션 칩은 항상 대각선 위(45° 회전)에만 놓인다(#29). 빗변의 중점을 기준으로 짝의 위 레인(짝수 슬롯)은 +18, 아래 레인은 −18만큼 빗변을 따라 어긋난다(`PAIR_STAGGER` 36, #44). 이웃 칩의 수직 거리 = 22/√2 ≈ 16px(짝 안 — 칩 높이 22라 6px 겹침, 참고 영상처럼 의도된 것), 46/√2 ≈ 33px(짝 사이)
- 서브에이전트 칩은 부모 대각선 양옆의 수평 구간에만 놓인다(#36): 오른쪽 수평(대각선 끝 커브 +38px부터)과 왼쪽 수평(대각선 시작 커브 −38px까지)에 번갈아(오른쪽 → 왼쪽 → …) 44px 간격. 화면 밖이나 다음 커브 안쪽으로는 가지 않는다(#22). 서브에이전트는 왼쪽 20% 회피를 적용하지 않고 가장자리 12px만 피한다(#37). 제목 배지는 `$USER`(#15)
- 세션은 실행 환경 그룹별로 묶여 블록을 이루고, 블록 사이에 3행을 비우며 그 행에는 선을 그리지 않는다(#41, #42, #49). 그룹 키: Warp 탭(`warp-tab:<window>-<tab>`; Warp의 상태 DB `warp.sqlite`에서 `terminal_panes.uuid`→`pane_nodes.tab_id`를 `sqlite3 -readonly`로 읽음, 없으면 `warpctrl pane list`, 5초 캐시, #43) → 없으면 Warp pane UUID → 터미널 프로그램 → desktop. 세션의 그룹이 바뀌면(탭 매핑이 뒤늦게 잡히거나 pane을 다른 탭으로 옮김) 새 블록의 가장 낮은 빈 슬롯으로 옮겨 붙는다. 같은 탭의 pane들은 붙어 있고, 다른 탭/프로그램 사이만 벌어진다. 블록 안에서 슬롯은 고정: 앞 세션이 사라져도 위로 당기지 않고, 새 세션은 그룹 안 가장 낮은 빈 슬롯을 받는다(#23). 앞 그룹이 커지거나 사라지면 뒤 블록이 옮겨지는데, 칩은 페이드하지 않고 자기 선에 얹힌 채 선과 함께 0.4초 동안 미끄러진다(`Rows`, #49): 새 행의 선은 왼쪽 끝에서부터 그려져 들어오고(칩은 선이 닿을 때 나타남), 살아남은 행은 이전에 그려지던 위치(행 단위, 진행 중이면 소수)에서 새 위치로 보간한다(`lane_params_at`). 짝 위/아래 어긋남도 같이 보간(`session_stagger_at`)
- 상태바(30px): 왼쪽 요약(세션/작업/입력 대기/idle 수), 가운데 호버 상세, 오른쪽에 플랜 사용량 배지 → SETTINGS → TEST 버튼. 사용량 배지는 창마다 `5H [▬▬▬░░] 22% ↻2H10M`처럼 이름 + 44×4 프로그레스 바 + 퍼센트 + 리셋 카운트다운으로 그린다(#48, #52). 바의 채움은 팔레트의 패킷 색이라 테마마다 알아서 맞고, 트랙은 잉크 18%. 첫 조회 성공 전에는 안 보이고, 15분 넘게 갱신에 실패하면 바까지 통째로 45%로 흐려진다. 로그인 없는 머신(API 키 사용자)에서는 영영 안 보인다
- 칩은 화면 왼쪽 20%(#30) 안쪽이나 오른쪽 가장자리 밖에 놓이지 않는다. 후보 자리(첫 스트라이프의 대각선 → 다음 스트라이프의 대각선 …) 중 화면 안에 들어오는 첫 자리를 쓴다(#27). 세션이 많으면 아래 레인의 대각선도 화면 안에 있도록 스트라이프 수를 늘린다
- 창 크기 변경 등으로 같은 선 위의 자리(스트라이프)가 바뀌면 옛 자리에서 0.22초 페이드아웃 후 새 자리에서 0.22초 페이드인(#28). 같은 자리 안에서 미끄러지는 것은 애니메이션 없이 따라간다. 자리 키에 레인 번호는 들어가지 않으므로 레인이 바뀌는 것만으로는 페이드하지 않는다(#49)
- 세션 칩 높이 22, 모서리 4, 좌우 패딩 13, 최소 폭 56. 서브 칩 높이 16 (#35: 칩 크기는 줄이지 않는다)
- 라벨: D-DIN Regular(`assets/fonts/D-DIN.ttf`, 바이너리에 `include_bytes!`로 내장)의 글리프 외곽선을 `ttf-parser`로 읽어 채우기 경로로 렌더링(#47, #55) — 45° 회전을 위해 경로로 그린다. `scale`은 캡 높이 = 6px × scale (세션 1.5 → 9px, 서브 1.1 → 6.6px, 제목 2.6 → 15.6px). 커닝(`kern`) 적용. 상태바·패널 등 gpui UI도 같은 서체 — 시작할 때 `ui::register_fonts`가 같은 바이트를 gpui에 등록한다(`theme::UI_FONT = "D-DIN"`, #46, #55)
- 소켓 24×14, 홈 6×6, 분리 시 칩 이동 16, 파형 길이 46, 진폭 6

## 검증 방법
화면 캡처 권한이 없어도 `cargo run -- --svg out.svg --demo --size 1920x1080` 로 같은 장면을 SVG로 뽑고 `swift tools/svg2png.swift out.svg out.png` 로 정확한 크기의 PNG를 만들어 확인한다. (Quick Look 썸네일은 비율을 무시하므로 쓰지 않는다.)

## 성능(#38)
- 선·라벨·칩 경로는 기하 해시를 키로 테셀레이션 결과를 캐시한다(`render/paint.rs`). 색은 그릴 때 입히므로 알파 애니메이션이 캐시를 깨지 않는다. 패킷(폭 12 미만)은 매 프레임 움직이므로 캐시하지 않는다.
- 화면 갱신은 vsync 대신 33ms 타이머(≈30fps), 세션 폴링은 1초. 측정: 66% → 8% CPU (M-series, 창 980×620).
- 캐시는 정점 예산(32만 정점 ≈ 10MB)으로 제한하고 예산 초과 시 이번 프레임에 안 쓴 항목을 버린다(#40). 메모리: 980×620 93MB, 2560×1440 99MB.
